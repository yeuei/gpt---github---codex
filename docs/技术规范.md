# 技术规范

> 本文件是项目当前技术实现的主真源之一。
> 本文件是本地触发器 V1 的当前技术真源；不保存浏览器登录态、cookie、密码、token 或其它秘密。
> 后续产生正式技术规范时直接原位更新本文件；历史通过 Git commit 查看。

## 1. 当前总流程

```text
Git remote branch
  ↓ poll / git fetch
Trigger parses Coordination-Origin + Coordination-Event-Id
  ↓ SQLite deduplication + dashboard audit
  ├─ agent → open-browser-use → configured ChatGPT Web conversation
  └─ chatgpt → explicitly configured local Agent command
  ↓
counterpart rereads GitHub HEAD before acting
```

## 2. 关键接口契约

输入是 Git commit metadata、`coordination/PR-<N>/` 文件变化以及 event trailers；输出是受控的唤醒操作和本机 SQLite 审计记录。

### 2.1 项目输入

- `Coordination-Origin`: `agent` 或 `chatgpt`
- `Coordination-Event-Id`: 在重试间保持稳定的唯一 id
- `Coordination-Caused-By`: 可选父 event id

### 2.2 项目输出

- Dashboard 中可见的 PR 时间线、event 状态和错误详情；
- `awaiting approval`、`dispatched`、`needs human` 或受控 `skipped` 状态；
- ChatGPT Web 的固定唤醒消息或本地 Agent 启动请求。

### 2.3 模型 / 工具

- Browser adapter：`open-browser-use` CLI + 用户手动启用的 Chrome extension；
- Web route：ChatGPT 普通 Chat 对话，不使用 Work 模式；
- Trigger runtime：Python 3 标准库、SQLite、git、`open-browser-use` CLI；
- Dashboard：仅监听 `127.0.0.1`。

## 3. 当前冻结参数

冻结的安全与控制参数：

- `approval_required=true` 为默认值：每条事件需在 Dashboard 单独批准；
- `auto_submit=false` 为默认值：即使已批准，ChatGPT 消息也只填入而不发送；
- `enabled`、`agent_to_chatgpt` 与 `chatgpt_to_agent` 可独立切换；
- 首次启动仅建立 Git baseline，绝不重放历史 commit；
- 没有 `agent.command` 时不得启动本地 Agent；
- 没有有效 `conversation_url` 时不得操作浏览器；
- 不读取 Chrome cookie、密码、session store 或不相关标签页。

普通工程细节（路径、manifest schema、row-id、deterministic seed、logging、retry、resume 等）默认由 Agent 自行决定，除非后续正式规范另有约束。

## 4. 数据 / Manifest

持久化内容仅包含本地 `trigger/state.sqlite3`：event id、commit SHA、PR number、origin、时间、状态和经过裁剪的错误信息。它被 `.gitignore` 排除。

未来遵循：

- manifest 路径、schema、row-id 编码等普通工程细节可由 Agent 自行冻结；
- 会改变实验/产品定义的数据源、比例、规模必须按权限规则由 ChatGPT 或用户决定；
- 必要时记录 source lineage / hash，确保正式输入可核验。

## 5. 运行与恢复

Trigger 的 polling 间隔由本地配置设置（默认 15 秒）。失败被记录为 `needs human`，不进行无限重试；用户修复浏览器/配置后可在 Dashboard 手动重新批准或重新触发新的 GitHub event。

未来普通工程实现（日志、progress、checkpoint、resume、failure handling）默认由 Agent 自行设计为可复现方案，无需为这些细节等待用户。

## 6. 验收条件

对任何正式 PR：

```text
代码存在 ≠ DONE
smoke 通过 ≠ formal DONE
```

只有当 `coordination/PR-<N>/任务.md` 中全部仍有效任务完成、无 BLOCKED / WAITING_USER，且代码/运行证据支持完成状态时，才可把总任务标为 `[x]`。

## 7. 禁止事项

- 不得用旧 runner 的行为反推当前规范；
- 不得用历史 smoke 替代正式运行；
- 不得把聊天记忆冒充 GitHub 当前事实；
- 不得因为局部 blocker 停止互不依赖任务；
- 不得无理由新增 smoke / benchmark / audit 延迟主线；
- 不得为保存历史创建 `技术规范_v2.md`、`final.md`、`latest.md` 等平行版本。

## 8. 版本更新原则

正式规范变化时：

```text
直接修改 docs/技术规范.md
```

Git commit 保存变化历史，HEAD 仅表达当前有效方案。

## 9. Binding 配对契约

配对是显式的三方路由记录，不以标题或浏览器状态推断身份。`binding_id` 标识一次配对，`route_id` 标识唯一路由；目标键为 `repository + branch + pr_number`，并记录 `web_conversation_id`、`local_agent_id`、`local_conversation_id`、`created_at`、`expires_at`、`updated_at`，名称字段仅作展示。

状态机：`pending → claimed → active`；`pending` 或 `claimed` 可因超时/人工撤销进入 `expired`/`revoked`，并在同一目标竞争时进入 `conflict`。创建邀请时生成短期一次性 token，服务端 SQLite 只保存哈希；claim 消费邀请 token 并返回一次性 confirm token，confirm 必须匹配原 route/Agent/Local 对话身份。一个目标最多一个 `active` binding，历史记录保留。

最小本地接口：`GET /api/bindings`（只读）、`POST /api/bindings/invite`、`/claim`、`/confirm`、`/revoke`；`POST /api/bindings/refresh-name/<binding_id>` 不读取 cookie 或标题，云端元数据不可用时返回明确错误。`binding.require_active` 默认关闭以兼容未配对的 V1；开启后未命中 active binding 的事件进入 `needs human`，命中后仅触发绑定的 Web 对话/Local Agent，不广播。
