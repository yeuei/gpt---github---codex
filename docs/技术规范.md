# 技术规范

> 当前技术真源。历史由 Git 保存，不创建 v2/final/latest 平行文档。

## 1. Runtime 架构

```text
Local Git clone
  ├─ refs/heads/*
  └─ refs/remotes/<remote>/*
       ↓ scan_local()（无网络）
Coordination trailers
       ↓
SQLite events / settings / bindings
       ↓
/api/status
       ↓
trigger/dashboard.html（唯一 renderer）
```

网络只有显式路径：

```text
POST /api/refresh-github
  ↓
git fetch <remote> --prune --quiet
  ↓ 成功
可选 gh pr list（若 gh 可用，仅同步 PR 元数据缓存）
  ↓
scan_local()
```

fetch 失败：不执行后续 scan，不修改事件审批/投递状态，返回 `local_state_preserved=true` 和准确错误。

## 2. Event 状态模型

SQLite `events` 当前有效字段：

- `approval_state`：`detected | awaiting | approved | auto_approved | not_applicable | legacy_unknown`
- `delivery_state`：`not_started | filled | submitted | agent_started | needs_human | skipped | legacy_unknown`
- `delivery_detail`：投递/执行详情
- `status/detail`：仅为已有 v1 DB 兼容保留，不作为新 UI 的状态真源

GitHub PR 状态不从上述字段推断。Dashboard 从显式同步缓存读取，否则显示 `unknown`。

## 3. Local Git 扫描

`GitSource` 只执行本地 Git 命令。首次看到某 ref 只建立 cursor baseline，不重放历史事件。事件以 `Coordination-Event-Id` 去重；缺少 event id 的旧提交退化到 commit SHA。

## 4. 历史任务快照

API：

```text
GET /api/task/snapshot?pr=<N>&sha=<40hex>
```

实现必须：

1. 验证真实 PR 整数和 40 位 SHA；
2. `git cat-file -e <sha>^{commit}`；
3. `git show <sha>:coordination/PR-<N>/任务.md`；
4. 解析该文本并返回。

任何失败返回 `available=false`。禁止调用当前工作树任务文件作为 fallback。

`GET /api/task/current?pr=<N>` 仅用于显式查看当前开放 PR 当前任务；它不能被节点详情自动当作历史快照。

## 5. Dashboard renderer

唯一实现：`trigger/dashboard.html`。

统一维护：

- 一个前端 state；
- 一个 `renderCanvas()`；
- PR/来源/审批/投递筛选；
- 指针拖动与滚轮缩放；
- 节点点击与详情；
- 节点 exact-SHA 任务读取。

旧 `HTML +=`、旧 table renderer、按时间匹配历史任务等逻辑全部退出当前运行路径。

## 6. 审批安全

Trigger 自动审批只影响 `approval_state` 和路由动作。`trigger/codex-agent-app-server.py` 继续以 `workspace-write + on-request` 独立向 Dashboard 发布 shell/file approval；Trigger 自动模式不能替代该审批。

## 7. Binding

保留 `binding.v1` 和 API：

- `GET /api/bindings`
- `POST /api/bindings/invite`
- `claim`
- `confirm`
- `revoke`
- `refresh-name/<binding_id>`

`/pair` 页面生成 invite 后用 URL fragment 封装一次性 token。

## 8. 兼容与迁移

已有 `state.sqlite3` 原位增加新列。旧记录没有可靠的审批/投递分离信息时显示 `legacy_unknown`，绝不从旧 `status` 猜测。

python3 -m unittest trigger/test_trigger.py -v

## 10. Dashboard 节点操作协议（Dashboard Node Action Protocol）

### 10.1 目标与范围（Goal and Scope）

Dashboard 不再只是观察界面：用户可以从一个已选中的流程节点发起**明确的人工修改请求**，让已配对的 GPT Web 对话重新读取当前 GitHub 状态并继续修改当前开放 PR。

本阶段只实现一个 MVP 动作：

```text
request_gpt_revision
```

右键菜单与 action 数据模型必须可扩展，但本 PR 不顺带实现“重试 Agent / 自动合并 / 改写历史 / 任意 Git 操作”等独立功能。

Dashboard action **不得直接修改 Git、GitHub 文件或历史 commit**。历史节点只是用户指出“我对这里不满意”的上下文锚点。

### 10.2 用户交互（User Interaction）

标准流程：

```text
选中节点
  ↓ 右键或节点详情中的同一操作入口
请求 GPT 修改
  ↓
弹窗显示只读节点信息
  - repository
  - PR number
  - event id
  - commit SHA
  - commit subject
  ↓
用户输入自然语言修改意见
  ↓
点击“发送给 GPT”
```

提交前不得自动发送。用户点击“发送给 GPT”本身即为这一次 action 的明确人工意图。

### 10.3 本地 Action 记录（Local Action Record）

SQLite 增加独立的 `dashboard_actions`（名称可由 Agent按工程实现微调，但语义不得改变），至少保存：

- `action_id`
- `action_type = request_gpt_revision`
- `repository`
- `target_pr_number`
- `target_event_id`
- `target_commit_sha`
- `target_ref`
- `user_instruction`
- `binding_id`（可空）
- `created_at`
- `dispatch_state`
- `dispatch_detail`
- `result_event_id`（可空）

`dispatch_state` 至少能区分：

```text
queued | sent | needs_binding | failed | cancelled
```

Action 投递状态、Trigger event 审批状态、GitHub PR 状态继续是三个不同事实域，禁止互相推断。

### 10.4 API 与校验（API and Validation）

提供语义等价于以下接口的本地 API：

```text
POST /api/actions/gpt-revision
GET  /api/actions?pr=<N>
```

提交时必须：

1. 从本地 SQLite 验证目标 event 确实存在；
2. 校验请求中的 event / PR / commit SHA 与本地节点一致，不能让前端任意伪造目标；
3. `user_instruction` 必须非空并设置合理长度上限；
4. 查找与目标 repository / branch / PR 匹配的 `active` binding；
5. 无 active binding 时记录 `needs_binding`，返回明确错误并引导用户到 `/pair`；
6. action 提交本身不得执行 `git fetch`，不得直接写 GitHub，也不得修改本地 Git 工作树。

### 10.5 路由选择（Routing Decision）

默认投递路径固定为：

```text
Dashboard
  ↓
Trigger action API
  ↓
active binding
  ↓
已配对的 ChatGPT Web conversation
```

**Codex CLI 不作为 Dashboard → GPT Web 的强制中转层。**

原因：现有 binding 已经定义 Web conversation 与本地项目/PR 的显式绑定；让 Codex CLI 再承担一次 relay 会增加状态、审批和故障点。Codex Agent 仍在 GPT 后续通过 GitHub 下发工程任务时参与执行。

### 10.6 投递给 GPT 的消息（GPT Wake Message）

投递消息至少包含：

```text
Dashboard 用户修改请求（Dashboard Revision Request）
Action-ID: <action_id>
Repository: <owner/repo>
Target-PR: #<N>
Target-Event: <event_id>
Target-Commit: <40hex>

用户修改意见：
<user_instruction>
```

同时必须附带行为约束：

1. 目标历史节点只作为上下文，不得 amend / force-push / rewrite 该历史；
2. GPT 行动前重新读取 GitHub 当前 PR 状态、当前 HEAD、当前 `任务.md`、必要时 `agent汇报.md` 与技术规范；
3. 目标 PR 仍开放时，在**当前 head** 上实现用户要求，而不是修改历史节点；
4. 目标 PR 已 merged/closed 时，不得假装还能继续修改原 PR，应按当前 Coordinator 协议判断是否需要新 PR；
5. GPT 新产生的有意义 commit subject 使用 `中文标题（English technical title）`；
6. 可关联的 GPT 协作 commit/event 应携带 `Coordination-Origin: chatgpt`，并用 `Coordination-Caused-By: dashboard-action:<action_id>` 建立因果关系。

不得把 binding token、cookie、credential 或其它 secret 放进该消息、SQLite 可展示字段、Git commit 或日志。

### 10.7 Dashboard 因果展示（Causal Rendering）

用户 action 应作为目标节点上的本地交互标记展示，并可查看其投递状态。

GPT 在 GitHub 产生新 commit 后，Dashboard **仍然不自动联网**。用户点击“从 GitHub 刷新”后：

```text
git fetch
  ↓
scan_local()
  ↓
发现 GPT 新 event
  ↓
若 Coordination-Caused-By = dashboard-action:<action_id>
  ↓
把新 GPT 节点与该用户 action 关联展示
```

历史节点继续严格按各自 commit SHA 读取任务快照，不能因为后续修改而回填旧节点。

### 10.8 安全边界（Safety Boundary）

- “发送给 GPT”只授权这次自然语言修改请求的投递；
- 不自动授予 Codex shell/file approval；
- 不自动 merge PR；
- 不自动 `git fetch`；
- 不自动重写历史；
- 不允许前端直接提交任意 shell command；
- 目标 PR 状态未知时可以投递，但 GPT 必须从 GitHub 重新核验；若本地缓存明确为 merged/closed，UI 应明确提示历史 PR 不可直接继续修改。

### 10.9 验收（Acceptance）

自动测试至少覆盖：

- 节点右键/详情操作入口与弹窗；
- 伪造 event/PR/SHA 被拒绝；
- 空修改意见被拒绝；
- 无 active binding → `needs_binding`；
- active binding → 构造包含 action id、目标 SHA 和用户意见的 GPT 消息；
- action API 不执行 GitHub fetch / Git 写入；
- action 投递状态与 event/PR 状态独立；
- `Coordination-Caused-By: dashboard-action:<id>` 可以关联后续 GPT event；
- 原有 single renderer、exact-SHA、local-first 测试继续通过；
- Python compile、unit tests、Dashboard JavaScript syntax、`git diff --check` 通过。

本机最终验收必须有一条真实 E2E—端到端证据：

```text
右键一个开放 PR 节点
→ 输入修改意见
→ GPT 配对对话真实收到请求
→ GPT 对该 PR 产生新的真实 GitHub 更新
→ 用户显式点击“从 GitHub 刷新”
→ Dashboard 显示对应的新 GPT 节点与 action 因果关系
```

该 E2E 必须由 Local Agent 在用户机器上运行并写入 `agent汇报.md`；CI 不能冒充本地浏览器运行证据。
