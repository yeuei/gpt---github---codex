# ChatGPT ↔ GitHub ↔ Codex 协作协议

## 1. 角色

### 用户（Human）

负责最终人工决策，尤其是会改变科研、产品或正式实验口径的问题。

### ChatGPT

负责：
- 读取 GitHub 当前状态；
- 分解任务并写 `任务.md`；
- 解决 Agent 上报的 blocker；
- 必要时进行网络研究；
- 写 `chatgpt解惑.md`；
- 无法替代用户决定时，提出最小化问题并请求用户。

### Codex Agent

负责：
- 本地代码、实验、脚本和运行；
- 普通工程决策；
- 收集当前本地事实；
- 更新 `任务.md` 状态；
- 覆盖 `agent汇报.md`；
- 将真正无法自行处理的问题上报。

## 2. 三文件协议

### 2.1 任务.md
性质：累积性任务合同。

ChatGPT：创建总任务、新增子任务、不根据猜测标 DONE。
Agent：只根据真实状态改任务标记，不擅自增加新的研究/产品目标。

### 2.2 agent汇报.md
性质：当前现实快照。Agent 每次重要 push 时完整覆盖。必须假设 ChatGPT 看不到本地文件，因此需要提供足以复现问题的上下文，但不得写 secrets。

### 2.3 chatgpt解惑.md
性质：ChatGPT 当前有效决策/解答。ChatGPT 每次需要改变当前指导时完整覆盖。一个 blocker 必须得到 `直接解决 / 授权 Agent / 请求用户` 之一。

## 3. 决策权限

### Agent 默认自行决定
- 路径、文件名、目录；
- manifest 的普通工程字段；
- deterministic seed；
- JSON/JSONL；
- retry、logging、resume；
- 普通 bug；
- 模块拆分和性能优化。

### ChatGPT 默认可以决定
- 并行/串行关系；
- blocker 是否真正阻塞主线；
- 当前实现是否符合规范；
- 是否授权 Agent 冻结工程细节；
- 是否需要外部研究。

### 用户必须决定
会显著改变项目正式口径的问题，例如核心数据源/比例、正式训练数据规模、模型替换、reward、benchmark、tool cap、核心算法或产品目标、对外核心结论。

## 4. 局部阻塞原则

`[!] BLOCKED` 只表示一个具体任务被阻塞，不表示整个 PR 停止。Agent 必须继续所有没有真实依赖的工作。

## 5. 旧代码原则

当前规范 > 当前代码 > 历史代码。被新规范覆盖的 legacy runner / prompt / config 可以阅读和借鉴，但不得因为历史上跑通就直接作为正式当前实现。

## 6. 文档原则

`Git history = 历史`，`HEAD = 当前`。同一语义的旧文档应删除；新规则直接覆盖当前文件。

## 7. 事件触发原则

未来自动触发系统收到 GitHub 事件后，只发送“唤醒消息”。唤醒消息不得承载正式任务定义。Agent/GPT 必须重新读取 GitHub 当前文件后再执行。同一 event_id 只能处理一次。

## 8. PR 合并后

- 保留代码和正式长期文档；
- 删除已完成 PR 的 coordination 工作目录；
- Git history 保留全部过程；
- 新任务创建新的 PR，而不是无限扩张旧 PR。

## 9. 三方 Binding 配对

ChatGPT 先创建真实仓库/PR，并在当前 Web 对话中明确生成短期一次性邀请（含稳定 `web_conversation_id`、repository、branch、pr_number）。Local Agent 认领后登记 `route_id`、`local_agent_id` 和 `local_conversation_id`；中转层只保存审计状态，确认完成后才是 `active`。标题是可刷新展示字段，不是路由键。

允许状态为 `pending`、`claimed`、`active`、`expired`、`revoked`、`conflict`。token 只用于一次认领/确认，仓库仅存哈希；重复认领、过期、目标不匹配、多 Agent 竞争必须显式失败。同一 repository/branch/PR 只能有一个 active binding；事件只投递给命中的 route 和 Web 对话，不广播。云端不可访问时，刷新名称只报告错误，不伪造更新。
