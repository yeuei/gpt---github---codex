# ChatGPT ↔ GitHub ↔ Local Agent 协作协议

## 1. 角色与边界

- 用户：决定会改变核心产品/研究口径或本机敏感授权的事项。
- ChatGPT：读取 GitHub 当前事实、拆分真实 PR 任务、解决规划 blocker、维护 `任务.md` 与 `chatgpt解惑.md`。
- Local Agent：执行本地代码/测试/运行，维护真实执行状态和 `agent汇报.md`。
- Dashboard：观察与审批界面，不成为任务真源。

## 2. Git 与 PR

`Git history = 历史`，`HEAD = 当前有效事实`。不得重写真实历史来“清理”状态。
一个 PR 只服务一个可关闭总目标。PR 合并后从 HEAD 删除其 `coordination/PR-N/`，历史仍由 Git 保存。

## 3. 三文件

- `任务.md`：累积任务合同，只增不减；状态只能依据真实证据更新。
- `agent汇报.md`：Agent 当前现实快照，覆盖更新。
- `chatgpt解惑.md`：ChatGPT 当前有效决策，覆盖更新。

## 4. Dashboard 本地优先协议

后台定时任务只允许：

```text
读取本地 refs → 读取本地 commit → 解析 Coordination-* trailer → 更新本地 SQLite
```

禁止后台自动 `git fetch`。网络同步只能通过明确的“从 GitHub 刷新”动作执行；网络失败必须返回原始/裁剪后的准确错误，并保留已有本地事件与状态。

## 5. 历史任务协议

事件节点 `(pr_number, commit_sha)` 的任务状态只来自：

```text
git show <commit_sha>:coordination/PR-<pr_number>/任务.md
```

不存在即 `unavailable`。禁止事件时间近似、当前任务回填、最终任务状态反推。

## 6. 状态协议

三类状态使用不同来源：

- `approval_state`：Trigger 本地审批事实；
- `delivery_state`：浏览器发送 / Agent 启动事实；
- `github_pr_state`：只有显式 GitHub PR 元数据同步才能更新；本地模式默认 `unknown`。

旧 v1 SQLite 记录如果只有混合 `status` 字段，新 runtime 只保留其 legacy 信息，不推断审批或投递状态。

## 7. 两个审批系统

Trigger event approval 与 Codex app-server command/file approval 独立。任何 UI 自动模式都不得跨层授权。

## 8. Binding

真实 repository/branch/PR 与一个 Web conversation、一个 Local Agent route 显式绑定。
一次性 invite → claim → confirm 后才是 `active`。token 只保存在本机 SQLite 哈希或一次性响应；分享链接 token 位于 URL fragment，不进入 GitHub、事件或服务日志。

## 9. Blocker

遇到 blocker 必须形成：直接解决 / 授权 Agent 自决 / 请求用户做最小决策之一。局部 blocker 不停止无依赖工作。
