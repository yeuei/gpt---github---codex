# ChatGPT ↔ GitHub ↔ Codex 协作协议

## 1. 角色

### 用户（Human）

负责最终人工决策，尤其是会改变科研、产品或正式实验口径的问题。

### ChatGPT

负责读取 GitHub 当前状态、分解任务并写 `任务.md`、解决 Agent blocker、必要时进行外部研究、维护 `chatgpt解惑.md`，以及在确实无法替代用户决定时提出最小化决策问题。

### Codex Agent

负责本地代码、实验、脚本和运行；普通工程决策；收集本地现实状态；更新任务状态；覆盖 `agent汇报.md`；并只上报真正无法在不改变正式口径的情况下自行解决的问题。

## 2. 三文件协议

### `任务.md`

累积性任务合同。ChatGPT 创建/追加任务；Agent 只根据真实执行状态修改状态。已完成任务不删除，被替代任务标 `[-] SUPERSEDED`。

### `agent汇报.md`

Agent 当前现实快照。每次重要 push 完整覆盖。必须假设 ChatGPT 看不到本地 working tree、shell、GPU、未 push 日志和未 push 数据，因此要提供足够的最小上下文，但不得写 secrets。

### `chatgpt解惑.md`

ChatGPT 当前有效决策/解答。每次新的核心指导产生时完整覆盖。每个 blocker 必须形成：`直接解决 / 授权 Agent / 请求用户最小决策` 之一。

## 3. 决策权限

### Agent 默认自行决定

- 路径、文件名、目录；
- manifest 的普通工程字段；
- deterministic seed；
- JSON/JSONL；
- retry、logging、resume；
- 普通 bug；
- 模块拆分、worker、batching、缓存与性能优化。

### ChatGPT 默认可以决定

- 子任务拆分与优先级；
- 并行/串行关系；
- blocker 是否真正阻塞主线；
- 当前实现是否符合规范；
- 旧实现是否已被新规范覆盖；
- 是否授权 Agent 冻结工程细节；
- 是否需要外部研究或最小必要验证。

### 用户必须决定

会显著改变项目正式口径的问题，例如：

- 核心数据源/比例；
- 正式训练数据规模；
- 模型替换；
- reward、benchmark、tool cap；
- 核心 prompt 的方法目标；
- 核心算法/产品路线；
- 对外核心结论。

## 4. 局部阻塞原则

`[!] BLOCKED` 只表示具体子任务被阻塞，不表示整个 PR 停止。所有没有真实依赖的工作必须继续。

## 5. 旧代码原则

规范定义代码应该做什么；代码只是规范实现。被新规范覆盖的 legacy runner / prompt / config 可以阅读和借鉴，但不得因为历史上跑通就直接作为当前正式实现。

## 6. 文档原则

```text
Git history = 历史
HEAD = 当前
```

同一语义的旧文档不应并列保留版本号副本；当前规则直接原位更新。

## 7. 启动与状态核验

每次新的 ChatGPT conversation 开始处理本仓库时：

1. 查询所有 open PR；
2. 读取每个 PR 的 `任务.md`；
3. 读取未完成、BLOCKED、WAITING_USER 项；
4. 读取目标 PR 的最新 `agent汇报.md`；
5. 必要时读取 `chatgpt解惑.md` 与当前技术规范；
6. 先用很短形式告诉用户当前未合并 PR 状态，再处理本轮问题。

如果 GitHub 当前无法读取，必须明确说明无法核验，禁止使用旧聊天记忆伪造进展。

## 8. PR 合并后

- 保留代码和正式长期文档；
- 删除已完成 PR 的 `coordination/PR-<N>/` 工作目录；
- Git history 保留全过程；
- 新的独立目标创建新 PR，而不是无限扩张旧 PR。

## 9. 安全

任何协调文档禁止写 API key、密码、access token、私钥、cookie 或其它秘密。需要描述 credential 时，只记录路径/slot/存在性/权限状态，不记录 secret value。
