# 触发器问题与解决方案

本文件只记录当前有效的触发器设计问题、证据和解决方案；被解决的问题原位更新为已解决，细节历史由 Git 保存。

## P1：普通 ChatGPT Chat 没有指定既有对话的公开消息注入 API

- 状态：`已采用受控 UI 路线`
- 影响：不能依赖 Work mode、ChatGPT API 或隐藏 API 来唤醒固定 Chat。
- 解决：本机 Trigger 用 `open-browser-use` 接管用户已登录且明确选择的 Chrome profile，导航/复用固定 conversation URL，并填入短唤醒消息。ChatGPT 仍运行在普通 Chat 模式。
- 边界：这不是绕过检测、验证码、速率限制或服务限制的方案。浏览器首次 extension 启用和任何自动发送都由用户明确批准。

## P2：`open-browser-use` 可被 LLM 使用，但本项目不应把固定路由交给 LLM 决策

- 状态：`已解决`
- 证据：CLI 提供 `ping`、`getUserTabs`、`claim-tab`、`open-tab`、`cdp` 和 `finalize-tabs`；SDK/MCP 只是可选入口。
- 解决：`trigger/trigger.py` 只调用固定 CLI/CDP 流程。LLM 不负责选择 tab、决定 URL 或生成发送内容。

## P3：错误/不一致 trailer 会导致事件漏发或重复

- 状态：`已解决，待真实闭环验证`
- 原因：旧 Agent Skill 使用 `Origin/Event/Dedup` 示例，而模板 YAML 已声明 `Coordination-*` 名称。
- 解决：统一为 `Coordination-Origin`、`Coordination-Event-Id`、可选 `Coordination-Caused-By`。SQLite 以 event id 去重，缺少 id 的旧提交退化为 commit SHA。

## P4：自动触发必须可暂停、可分方向控制且能人工介入

- 状态：`已实现本地设计，待运行验证`
- 解决：Dashboard 有全局 `enabled`、`agent_to_chatgpt`、`chatgpt_to_agent`、`approval_required` 和 `auto_submit` 独立开关。默认每条事件进入 `awaiting approval`；批准前不得向 ChatGPT 填写消息或启动 Agent。

## P5：GitHub commit 与 PR 的关联可能不总能从 commit metadata 得到

- 状态：`待真实 PR 验证`
- 当前方案：优先从本次 commit 修改的 `coordination/PR-<N>/` 路径提取 PR number；没有路径时记录为 `unassigned`，不伪造 PR 号。
- 后续：如真实 PR 证明这一规则不足，再接入 GitHub PR API 映射，并将权限/速率限制错误记录为 `needs human`。

## P6：首次浏览器配置需要人工操作

- 状态：`等待用户`
- 所需动作：用户运行 `open-browser-use setup`，在选择的 Chrome profile 中安装/启用扩展，保持 Chrome 打开；之后可用 `open-browser-use profiles --connected --json` 和 `ping` 验证。
- 不可替代性：Trigger 不会自动安装 extension、读取登录态或在多个 profile 中擅自选择一个。

## P7：本地 Agent 启动命令不能由 Trigger 猜测

- 状态：`等待用户`
- 解决：`trigger/config.local.json` 的 `agent.command` 默认为空。未配置时批准事件显示 `needs human`，不会执行 shell 或启动不确定的 Codex 会话。

## P8：只轮询 main 会漏掉尚未合并 PR 的交接

- 状态：`已解决，baseline 已验证`
- 原因：真实 Agent/ChatGPT 协作发生在 PR head branch；main-only polling 只能在合并后看见，已经错过唤醒。
- 解决：Trigger 默认 `watch_branches: "all"`，为每个 `origin/<branch>` 维护独立 cursor。首次看到一个 branch 只建立 baseline；之后的新 commit 才成为事件。同一个 event id 进入 main 时仍由 SQLite 全局去重。

## P9：本地 Dashboard 的首次 Agent-origin 路由验证

- 状态：`执行中`
- 验收：一个带标准 `Coordination-Origin: agent` 与 `Coordination-Event-Id` 的真实远端分支 commit 在 Dashboard 中显示为 `awaiting approval`，且不会在批准前接管 Chrome 或启动 Agent。
- 限制：该验证发生在真实 PR 创建前，因此 PR 号应诚实显示为 `unassigned`；不得伪造 PR number。

## 下一次真实闭环检查

1. 创建本项目真实 PR，并实例化 `coordination/PR-<真实编号>/`；
2. 启动 Trigger，确认第一轮只建立 baseline；
3. Agent-origin push 进入待审批队列；
4. 用户批准后验证 ChatGPT Web 被填入/发送唤醒；
5. remote ChatGPT 的 GitHub 更新带上反向 trailer；
6. 该更新进入待审批队列，批准后只启动一次 local Agent；
7. 检查 SQLite/Dashboard 时间线、无重复路由、无未解释失败；若任一环失败，原位更新本文件和基础协议仓库。
