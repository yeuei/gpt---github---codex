# 触发器问题与解决方案

本文件只记录当前有效的触发器设计问题、证据和解决方案；被解决的问题原位更新为已解决，细节历史由 Git 保存。

## P1：普通 ChatGPT Chat 没有指定既有对话的公开消息注入 API

- 状态：`已采用受控 UI 路线`
- 影响：不能依赖 Work mode、ChatGPT API 或隐藏 API 来唤醒固定 Chat。
- 解决：本机 Trigger 用 `open-browser-use` 接管用户已登录且明确选择的 Chrome profile，导航/复用固定 conversation URL，并填入短唤醒消息。ChatGPT 仍运行在普通 Chat 模式。
- 边界：这不是绕过检测、验证码、速率限制或服务限制的方案。浏览器首次 extension 启用和任何自动发送都由用户明确批准。

## P2：`open-browser-use` 可被 LLM 使用，但本项目不应把固定路由交给 LLM 决策

- 状态：`已解决`
- 证据：CLI 提供 `ping`、`getUserTabs`、`claim-tab`、`open-tab`、`cdp` 和 `finalize-tabs`；SDK/MCP 只是可选入口。
- 解决：`trigger/trigger.py` 只调用固定 CLI/CDP 流程。LLM 不负责选择 tab、决定 URL 或生成发送内容。

## P3：错误/不一致 trailer 会导致事件漏发或重复

- 状态：`已解决，待真实闭环验证`
- 原因：旧 Agent Skill 使用 `Origin/Event/Dedup` 示例，而模板 YAML 已声明 `Coordination-*` 名称。
- 解决：统一为 `Coordination-Origin`、`Coordination-Event-Id`、可选 `Coordination-Caused-By`。SQLite 以 event id 去重，缺少 id 的旧提交退化为 commit SHA。

## P4：自动触发必须可暂停、可分方向控制且能人工介入

- 状态：`已实现本地设计，待运行验证`
- 解决：Dashboard 有全局 `enabled`、`agent_to_chatgpt`、`chatgpt_to_agent`、`approval_required` 和 `auto_submit` 独立开关。默认每条事件进入 `awaiting approval`；批准前不得向 ChatGPT 填写消息或启动 Agent。

## P5：GitHub commit 与 PR 的关联可能不总能从 commit metadata 得到

- 状态：`待真实 PR 验证`
- 当前方案：优先从本次 commit 修改的 `coordination/PR-<N>/` 路径提取 PR number；没有路径时记录为 `unassigned`，不伪造 PR 号。
- 后续：如真实 PR 证明这一规则不足，再接入 GitHub PR API 映射，并将权限/速率限制错误记录为 `needs human`。

## P6：首次浏览器配置需要人工操作

- 状态：`已验证`
- 所需动作：用户运行 `open-browser-use setup`，在选择的 Chrome profile 中安装/启用扩展，保持 Chrome 打开；之后可用 `open-browser-use profiles --connected --json` 和 `ping` 验证。
- 不可替代性：Trigger 不会自动安装 extension、读取登录态或在多个 profile 中擅自选择一个。
- 运行证据：选择的 Chrome profile 在完全退出、重启后，`open-browser-use ping --browser chrome --profile Default` 返回 `pong`；说明 native-host 会话能自行恢复。

## P7：本地 Agent 启动命令不能由 Trigger 猜测

- 状态：`等待用户`
- 解决：`trigger/config.local.json` 的 `agent.command` 默认为空。未配置时批准事件显示 `needs human`，不会执行 shell 或启动不确定的 Codex 会话。

## P8：只轮询 main 会漏掉尚未合并 PR 的交接

- 状态：`已解决，baseline 已验证`
- 原因：真实 Agent/ChatGPT 协作发生在 PR head branch；main-only polling 只能在合并后看见，已经错过唤醒。
- 解决：Trigger 默认 `watch_branches: "all"`，为每个 `origin/<branch>` 维护独立 cursor。首次看到一个 branch 只建立 baseline；之后的新 commit 才成为事件。同一个 event id 进入 main 时仍由 SQLite 全局去重。

## P9：本地 Dashboard 的首次 Agent-origin 路由验证

- 状态：`已通过`
- 证据：`feature/local-trigger-v1` 的 commit `1cc4faf`（event `ggc-local-routing-smoke-001`）被守护程序记录于 `2026-09-04T09:31:09Z`，状态为 `awaiting approval`。
- 验收：一个带标准 `Coordination-Origin: agent` 与 `Coordination-Event-Id` 的真实远端分支 commit 在 Dashboard 中显示为 `awaiting approval`，且不会在批准前接管 Chrome 或启动 Agent。
- 限制：该验证发生在真实 PR 创建前，因此 PR 号应诚实显示为 `unassigned`；不得伪造 PR number。

## P10：一次 browser/configuration 错误不能使同一事件不可恢复

- 状态：`已验证`
- 解决：Dashboard 对 `needs human` 事件显示 Retry。用户修复 extension、profile、conversation URL 或 Agent command 后可重新批准同一 event id；不会生成重复 GitHub commit 或绕过去重保护。
- 运行证据：早期 event `ggc-local-routing-smoke-001` 因 socket 未就绪进入 `needs human`；在浏览器连通后，另一个 unassigned event `ggc-pr-bootstrap-001` 被批准并进入 `dispatched`，详情为 `filled; waiting for user submit`。批准前 `auto_submit=false`，没有代表用户发送消息。

## P11：首次实现分支没有 PR 时，不能让启动流程陷入“先有 PR 才能交接”的循环

- 状态：`已解决，待 remote ChatGPT 验证`
- 原因：三文件目录必须使用真实 PR 号，但触发器的第一条 Agent event 可能恰好来自尚未创建 PR 的分支。
- 解决：unassigned event 的唤醒消息包含实际 branch 与 head SHA，并要求 remote Coordinator 先核验该分支是否是一项可关闭工作；只有确实如此并拥有 GitHub 写权限时，才创建真实 PR，随后从 `coordination/TEMPLATE/` 实例化对应真实目录。

## P12：诊断运行环境可能无权连接 owner-only Unix socket，不能把其失败误判为扩展故障

- 状态：`已解决并记录部署边界`
- 原因：Open Browser Use 的 extension 不通过 HTTP/CORS 通信。它以 `chrome.runtime.connectNative()` 连接本机 native host；native host 在 `/tmp/open-browser-use/*.sock` 创建仅当前 macOS 用户可访问的 Unix socket，CLI/Trigger 经 `active.json` 定位该 socket。
- 证据：native host 能在普通 macOS 上以 Chrome 传入的 extension origin 参数启动并创建 socket；真实 Chrome 会话随后使 `ping` 返回 `pong`。但 Codex 的受限命令环境尝试 bind/connect 同一 socket 会得到 `operation not permitted`，即假阴性。
- 解决：部署 Trigger 时必须让它作为用户本机常驻进程运行，而非以受限 Codex 工具进程作为生产运行时。健康检查的权威结果是该本机进程的 `open-browser-use ping`，不是受限诊断 shell 的失败输出。

## P13：向 ChatGPT ProseMirror 编辑器直接写 DOM 可能产生“已填入”的假成功

- 状态：`已验证`
- 证据：旧实现对 `#prompt-textarea` 直接赋 `textContent` 并分发 `InputEvent`。Dashboard 因 CDP 命令无异常而显示 `filled`，但目标 ChatGPT 输入框实际长度为 `0`；远程对话没有新消息是预期的，因为并未真正写入草稿。
- 解决：先定位精确的 ProseMirror editor；发现用户已有草稿时拒绝覆盖；不再依赖后台 tab 上未被 ChatGPT 保留的 CDP `Input.insertText`，而使用 Chromium 的 `document.execCommand('insertText')` 让编辑器接收原生 `input`；随后等待最多 2.5 秒，轮询 ProseMirror 与 ChatGPT fallback textarea 的实际内容并做精确回读。若重试时草稿已经等于目标消息，则直接视为已验证，避免覆盖。任何一个阶段失败均为 `needs human`，不得显示 `dispatched`。
- 最新人工复核：Chrome 的 ChatGPT 输入框确实显示完整唤醒消息，说明写入动作已到达页面；此前“未保留”主要是即时回读早于页面同步造成的假失败。
- 最终运行证据：`2026-09-04T14:09:10+00:00`，Dashboard 将 `ggc-pr-bootstrap-001` 标为 `已执行`，详情为 `filled; verified; waiting for user submit`；Chrome 目标编辑器可读到同一 `Event-ID` 的完整草稿，且没有触发发送。

## P15：扩展状态 Connected 不等于 CLI 当前有可用 socket

- 状态：`已验证，持续监控`
- 现象：Open Browser Use 扩展弹窗显示 `Connected / Native host is connected and ready`，但 `/tmp/open-browser-use/active.json` 指向的 socket 文件已不存在，CLI `ping` 因此报告 `no Open Browser Use socket found`。
- 结论：扩展到 native host 的连接状态和 CLI relay socket 是两层状态；触发器必须记录 CLI ping 的实时结果，不能只依据扩展弹窗颜色判断可用性。若 socket registry 残留，应按 troubleshooting 流程重启/唤醒所选 Chrome profile 后再重试，不能把该现象归因于 CORS。
- 当前实现：触发器复用长期 OBU session，不在每个事件后调用 `turn-ended`；后台周期性 ping，并提供 `/api/browser/check` 与前端“检测浏览器连接”按钮。发现 registry 指向已删除 socket 时只清理该 registry 并重试；若 native host 本身确实退出，前端明确显示 `无法连接` 及 CLI 原因，不伪装成已执行。
- 最终运行证据：首次重试时确实遇到 `no Open Browser Use socket found`；在保留 Chrome 不重启的情况下，下一次检测清理失效 registry 后于 `2026-09-04T14:07:08+00:00` 恢复 `OBU ping 成功`，随后 `14:09:10+00:00` 完成草稿验证。这证明常见的 stale registry 不再要求用户重启浏览器。

## P14：Open Browser Use 的 JSON-RPC 错误与 handoff tab 所有权必须显式处理

- 状态：`已修复，待真实浏览器复验`
- 证据：旧代码只检查 CLI 进程退出码，忽略 JSON 内的 `error`。当目标 tab 仍属于旧 `handoff` session 时，`claim-tab` 返回“already part of browser session”，代码仍继续向新 session 发 CDP 命令，最终报“tab is not part of browser session”。
- 解决：所有 `getUserTabs`、`claim-tab`、`open-tab` 与 CDP 操作均解析 JSON-RPC result/error；错误立即进入 `needs human`。仅在草稿已回读验证、等待用户发送时保留 `handoff`；其它失败路径以可重认领的 `deliverable` 结束并调用 `turn-ended`。已加入回归测试，确保 RPC error 不会被误判为成功。
